 + Leading idea (2026-08-19), may replace the positional-stack-climber idea below: `./`/`../`/`.../` as project-tier scope operators instead, old-school style. `./` is your own project's global scope (first-party). `../` reaches into `2nd/` at the project root (second-party libraries), `.../` into `3rd/` (third-party/vendored code, potentially non-Tape once FFI exists). Only three fixed tiers, not open-ended chaining. A different axis entirely from the stack-climber idea (module/dependency-tier resolution, not runtime call-stack depth) -- probably lives in `@load`/file-resolution, not `scope_for_identifier`. Doesn't conflict with `self`/`Self` (those stay the instance/type accessors either way).
   + Mechanism: new interpreter class-level `second_party_scope`/`third_party_scope`, each with its own Global instance, not shared with the user's own -- same anchoring pattern `@stdlib_scope` already uses. `../Ident`/`.../Ident` pull a single identifier straight out of that scope (`tool1 := .../Tool` reaches into `3rd/tool.tape` for `Tool{}` without loading anything else); `@load '3rd/tool.tape'` still loads the whole file bare, and `x := @load '3rd/tool.tape'` still namespaces it under `x`, same as `@load` already works today -- `../`/`.../` are a third, narrower option alongside the two existing `@load` forms, not a replacement for either.
   + Open question: unlike stdlib (reachable via a bare identifier too, through Global's readable-scope fallback), should 2nd/3rd-party scopes be excluded from ordinary bare-identifier search entirely, reachable *only* via the explicit `../`/`.../` prefix? Seems necessary for the sandboxing goal (a 2nd-party library's `Tool` shouldn't silently shadow or collide with the user's own `Tool` just by being loaded).
   + Ties into "Opaque scopes" (not yet designed): full sandboxing needs isolation in both directions -- user code reaching *into* 2nd-party internals only via the explicit pull (above) is one direction, but 2nd-party code itself reaching *out* to the user's global via its own `~/` while it's executing is the other. `~/` today is just `stack.first`, unconditionally; opaque scopes would need `~/` (and anything else that currently assumes one single global) to resolve relative to *whichever* sandbox is currently executing, not always the same fixed one.
   + Candidate mechanism for the "opaque" direction (corrected 2026-08-19, no swap involved): still one single `stack`, not two swapped ones. A whole second-party stack pushes onto it as one unit, so the array can hold a mix of plain scopes and pushed sub-stacks, e.g. `[Global, [Seconds_Global, ...], <current_scope>]`. The actual new rule is a search-time guard, not an activate/deactivate step: a `Global` is a hard wall, reverse search (`find_in_stack`, `scope_for_identifier`'s bare-identifier case, anything walking `stack.reverse_each`) stops the instant it crosses *any* Global, never continues past it -- so from inside second-party execution, search can climb up through its own frames and hit *its* Global, but never falls through to the user's outer Global underneath. Today this rule is vacuously already true (there's only ever one Global, always at index 0, nothing ever sits past it), so nothing regresses; it only starts doing real work once a second Global can exist mid-stack. Wrinkle resolved (2026-08-19): a *later*, cross-boundary call (user code holding a reference to a 2nd-party instance, calling a method on it after the fact, with the pushed sub-stack long gone) works the same way an ordinary instance method call already pushes `func.enclosing_scope`'s Instance/Type chain before running (`interp_func_body`, `push_scope type.enclosing_scope`/`push_scope type`/`push_scope func.enclosing_scope`) -- a Func/Type declared inside a realm remembers that origin the same way it already remembers its enclosing Instance/Type, and calling it pushes that realm's stack too, one more link added to a chain that already exists, not a new concept.
